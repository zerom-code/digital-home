# 05. Архитектура

## Стек клиента

| Слой | Выбор | Почему |
|---|---|---|
| Сборка | **Vite + React + TypeScript** | статика на CDN, полный контроль над service worker |
| PWA | **vite-plugin-pwa** (Workbox) | манифест, precache, стратегии кеширования, поток обновления |
| Данные | **TanStack Query** + persister в IndexedDB | кеш переживает перезапуск, чтение офлайн получается почти бесплатно |
| Офлайн-запись | **Dexie** (таблица `outbox`) | очередь мутаций и повтор при появлении сети |
| UI-состояние | **Zustand** | лёгкое, без бойлерплейта; серверное состояние живёт в Query |
| Формы | **react-hook-form + zod** | одна zod-схема используется и для валидации формы, и для Structured Outputs в ИИ-слое |
| Стили | **Tailwind + shadcn/ui** | быстрый мобильный UI, доступные примитивы (Radix), легко задать крупные тач-зоны |
| Роутинг | **React Router** | вложенные маршруты хорошо ложатся на дерево дома |
| i18n | **i18next** | ключи с первого дня, локаль пока только `ru` |
| Тесты | **Vitest + Testing Library**, **Playwright** | энергоформулы и офлайн-очередь обязаны быть под тестами |

### Почему Vite, а не Next.js

Приложению не нужен SSR: это персональный инструмент за авторизацией, SEO
нерелевантен, а первая отрисовка после установки идёт из кеша service worker,
а не с сервера. При этом Next.js усложняет ровно то, что здесь критично —
контроль над service worker и офлайн-поведением. Vite даёт статический бандл,
который кладётся на CDN и работает.

## Бэкенд: Supabase

- **Auth** — email OTP (без паролей: меньше трения, особенно для «мамы»),
  плюс Google и Apple.
- **Postgres + RLS** — вся авторизация в базе. Клиент ходит в неё напрямую,
  промежуточного API нет. Детали — в [02-data-model.md](02-data-model.md).
- **Storage** — приватные бакеты, доступ через signed URL.
- **Realtime** — подписка на изменения своей семьи: второй участник видит
  правки сразу.
- **Edge Functions** — `accept-invite`, `send-push`, `generate-passport-pdf`,
  группа `ai-*` (см. [08-ai.md](08-ai.md)).
- **pg_cron** — ежедневная задача: находит истекающие гарантии, наступившие
  интервалы ТО и сроки замены расходников, создаёт задачи и ставит пуши в
  очередь.
- **pgvector** — эмбеддинги фрагментов инструкций.

### Почему без своего API-слоя

RLS уже является слоем авторизации, и дублировать его в Node-сервисе — значит
получить два места, где правила могут разойтись. Логика, которую нельзя
доверить клиенту (приём приглашений, обращения к OpenAI, генерация PDF),
живёт в Edge Functions — их немного, и они точечные.

## Офлайн

Выбранная модель: **чтение офлайн + очередь записи.**

```
Чтение
  Supabase → TanStack Query → persist в IndexedDB
  При старте кеш поднимается мгновенно, сеть догоняет фоном.

Запись
  мутация
    → оптимистично в кеш Query
    → строка в Dexie.outbox
    → воркер отправляет при online, экспоненциальный бэкофф
    → успех: убрать из outbox
    → конфликт: last-write-wins по updated_at, расхождение в журнал,
      пользователю — баннер «Изменения разошлись»

Файлы
  Blob кладётся в IndexedDB, загрузка в Storage — отдельная очередь:
  файлы большие, и их отправка не должна блокировать мелкие правки.

Идентификаторы
  UUID генерирует клиент → повторная отправка идемпотентна (upsert),
  дублей не будет.
```

### Почему не CRDT

ElectricSQL, PowerSync, Replicache и Yjs решают задачу одновременного
редактирования одной сущности несколькими людьми в реальном времени. Здесь
такой задачи нет: члены семьи редактируют разные вещи, коллизии редки и
некритичны (кто последний поправил название холодильника — тот и прав).
Полноценный синк добавил бы существенную сложность, ещё одну инфраструктурную
зависимость и стоимость — ради сценария, который почти не встречается.

Модель можно будет заменить позже: очередь мутаций изолирована в
`src/lib/outbox`, и остальной код о ней не знает.

## PWA на iOS и Android

### iOS — реальные ограничения

- **Push работает только у приложений, добавленных на домашний экран**
  (iOS 16.4+, март 2023). Во вкладке Safari `PushManager` недоступен. Значит,
  запрашивать разрешение на уведомления имеет смысл только после установки.
- **Нет `beforeinstallprompt`.** Нужен собственный экран-подсказка
  «Поделиться → На экран „Домой“» с картинкой. Без него установку просто не
  найдут, а без установки не будет уведомлений.
- **Нет Background Sync.** Очередь отправляем при открытии приложения и по
  событию `online`, а не в фоне.
- **Данные могут вытесняться** при длительном неиспользовании. Поэтому
  источник истины — всегда сервер, а IndexedDB только кеш. Ничего, что
  существует лишь локально, быть не должно.
- **Safe-area insets** (`env(safe-area-inset-bottom)`) обязательны, иначе
  нижняя панель уезжает под системный индикатор.
- Историю с удалением домашних веб-приложений в ЕС по DMA Apple отменила
  в марте 2024 — они работают. Для Украины вопрос в любом случае неактуален.

### Android

- `beforeinstallprompt` перехватываем и показываем собственную кнопку
  «Установить» в подходящий момент, а не сразу при первом заходе.
- Maskable-иконки 192 и 512px, `theme_color`, `display: standalone`, WebAPK.

### Сканирование штрихкодов

`BarcodeDetector` в WebKit отсутствует, то есть не работает **ни в одном
браузере на iOS**. Решение: `zxing-wasm` как основной путь, нативный
`BarcodeDetector` — как ускорение там, где он есть. WASM-бандл около 2 МБ,
поэтому грузится лениво, только при открытии сканера.

### Стратегии кеширования

| Тип запроса | Стратегия |
|---|---|
| Оболочка приложения (JS, CSS, HTML) | precache + `CacheFirst` |
| Иконки, шрифты | `CacheFirst`, долгий срок |
| Фотографии из Storage | `StaleWhileRevalidate`, ограничение по количеству |
| Данные из Supabase | не кешируем в SW — этим занимается TanStack Query |

### Обновление версии

Новый service worker не активируется молча. Показывается тост «Доступна новая
версия · Обновить»; принудительной перезагрузки нет — пользователь может
дописать то, что начал.

## Структура кода

```
src/
├── app/                # роутинг, провайдеры, layout, error boundary
├── features/
│   ├── auth/
│   ├── household/      # семья, приглашения, роли
│   ├── home/           # дома, комнаты, дерево
│   ├── items/          # вещи, карточка, поиск
│   ├── documents/      # загрузка и просмотр
│   ├── tasks/          # гарантии, ТО, расходники
│   ├── energy/         # профили, тарифы, счётчики, экран
│   └── ai/             # клиентские обёртки над ai-* функциями
├── components/ui/      # shadcn
├── lib/
│   ├── supabase/       # клиент, типы из БД
│   ├── outbox/         # офлайн-очередь
│   ├── energy/         # чистые функции расчёта (полностью покрыты тестами)
│   ├── i18n/
│   ├── viewport.ts     # --app-h и --kb-h: каркас окна на iOS (ADR-018)
│   └── utils/
└── data/               # справочники, загружаемые в рантайме
```

Каждая папка в `features/` содержит свои компоненты, хуки и запросы. Общее
поднимается в `lib/` только когда переиспользуется реально, а не «на будущее».

## Переменные окружения

Клиент (попадают в бандл, ничего секретного):

```
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY      # публичный по замыслу, защита — RLS
VITE_APP_URL
VITE_VAPID_PUBLIC_KEY
```

Только в секретах Supabase:

```
OPENAI_API_KEY
VAPID_PRIVATE_KEY
SUPABASE_SERVICE_ROLE_KEY
```

Шаблон — в [`.env.example`](../.env.example).

## Хостинг и CI

- Статика — Cloudflare Pages, Netlify или Vercel; принципиальной разницы нет,
  нужен только CDN с корректными заголовками для service worker
  (`Cache-Control: no-cache` на `sw.js`).
- Миграции применяются через Supabase CLI из `supabase/migrations`.
- GitHub Actions: типы, линт, юнит-тесты на каждый PR; Playwright — на ветке
  по умолчанию; preview-деплой на PR.
