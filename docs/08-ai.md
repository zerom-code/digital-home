# 08. ИИ-слой

Модель: **gpt-4o-mini** (vision + Structured Outputs), эмбеддинги —
`text-embedding-3-small`.

## Зачем он здесь

Не «прикрутить ИИ, потому что модно». В этом продукте у языковой модели есть
ровно одна стратегическая работа — **уничтожить главный риск: ручной ввод
данных.** Всё остальное приятно, но вторично.

Человек не станет вводить модель, серийный номер и мощность холодильника
руками. Но сфотографировать табличку на задней стенке он готов. Вся ценность
ИИ-слоя в этом зазоре.

## Железное правило

> **Цифры считает код. Модель читает, раскладывает по полям и объясняет.**

Энергорасчёты, сроки гарантии, стоимость владения — детерминированный
TypeScript под тестами. Модель никогда не выполняет арифметику и никогда не
пишет в базу напрямую: она возвращает **черновик формы**, который подтверждает
человек.

Обоснование — в [ADR-008](07-decisions.md). Коротко: ошибка распознавания
модели заметна и легко правится, ошибка в сумме гривен незаметна и убивает
доверие ко всему приложению.

**В интерфейсе:** поля, заполненные моделью, помечены значком ✨ — видно, что
стоит проверить.

## Сценарии

### S-tier — ради этого стоит подключать

#### 1. Фото шильдика → заполненная карточка

На каждой единице техники есть табличка с моделью, серийным номером,
мощностью, напряжением и годом выпуска. Пользователь её фотографирует —
карточка заполняется сама.

Это превращает восемь полей ручного ввода в один тап и **попутно даёт точную
мощность для энергорасчёта** — то самое число, которое человек никогда бы не
ввёл руками.

Схема ответа (`ai-extract-nameplate`):

```json
{
  "name": "nameplate",
  "strict": true,
  "schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["brand","model","serial_number","power_w","voltage",
                 "year","category_hint","confidence"],
    "properties": {
      "brand":         {"type": ["string","null"]},
      "model":         {"type": ["string","null"]},
      "serial_number": {"type": ["string","null"]},
      "power_w":       {"type": ["number","null"],
                        "description": "Номинальная мощность в ваттах"},
      "voltage":       {"type": ["number","null"]},
      "year":          {"type": ["integer","null"]},
      "category_hint": {"type": ["string","null"],
                        "description": "id категории из справочника, если понятно"},
      "confidence":    {"type": "string", "enum": ["low","medium","high"]}
    }
  }
}
```

Промпт: *«На фотографии — заводская табличка бытовой техники. Извлеки данные.
Если поле не читается или его нет — верни null, не догадывайся. Мощность
приведи к ваттам: 1.5 kW → 1500.»*

Обратите внимание на структурное совпадение: `strict: true` требует, чтобы
**все** поля были в `required`, а необязательность выражалась через nullable-тип.
Это ровно та же модель, что и в базе ([ADR-006](07-decisions.md)) — «всё
nullable, ничего не выдумываем».

#### 2. Фото комнаты → список техники

«Сфоткай кухню» вместо «заполни форму». Модель находит на снимке холодильник,
плиту, вытяжку, чайник и микроволновку и предлагает создать карточки —
пользователь снимает галочки с лишнего.

Самый сильный онбординг, который вообще возможен для такого приложения:
квартира заполняется четырьмя фотографиями.

```json
{
  "name": "room_scan",
  "strict": true,
  "schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["items"],
    "properties": {
      "items": {
        "type": "array",
        "items": {
          "type": "object",
          "additionalProperties": false,
          "required": ["name","category_id","brand","confidence"],
          "properties": {
            "name":        {"type": "string"},
            "category_id": {"type": ["string","null"]},
            "brand":       {"type": ["string","null"]},
            "confidence":  {"type": "string", "enum": ["low","medium","high"]}
          }
        }
      }
    }
  }
}
```

Список допустимых `category_id` передаётся в промпт из справочника — так
модель не изобретает своих категорий.

#### 3. Вопросы к инструкции (RAG)

Инструкции никто не читает, но все ищут в них одно и то же: «что означает
ошибка E24», «как включить быструю заморозку», «какой фильтр подходит».

Коды ошибок — killer-кейс всего раздела: человек стоит перед мигающей
посудомойкой и получает ответ за пять секунд вместо получаса поисков.

Как устроено:

1. При загрузке PDF текст извлекается (pdf.js на клиенте либо в Edge Function).
2. Режется на фрагменты по ~800 токенов с перекрытием, с сохранением номера
   страницы.
3. Эмбеддинги `text-embedding-3-small` (1536 измерений) кладутся в
   `document_chunks` с индексом HNSW.
4. Вопрос → эмбеддинг → поиск ближайших фрагментов **в пределах своей семьи**
   (RLS по `household_id`) → ответ с указанием страницы.

Ответ всегда содержит ссылку на источник: «Стр. 24 инструкции». Если
релевантных фрагментов не нашлось — честное «в инструкции этого нет», а не
выдуманный ответ.

### A-tier

#### 4. Фото чека → вещь с датой, ценой и магазином

Один чек часто даёт несколько позиций и, что важнее, **дату покупки** — из
неё автоматически считается гарантия. Пользователь фотографирует чек один раз
при покупке и больше о нём не думает.

#### 5. Нормализация свободного ввода

«самсунг холодильник ноуфрост» → бренд `Samsung`, категория `kitchen.fridge`,
типовая мощность, типовой срок гарантии.

Сопоставление живого текста со справочником категорий — задача, где модель
объективно лучше регулярных выражений, и при этом ошибка ничем не грозит:
пользователь видит результат и правит.

#### 6. Поиск на естественном языке

«где инструкция от бойлера», «что на кухне ест больше всего», «что мы покупали
в 2023».

**Модель не пишет SQL.** Она вызывает предопределённые инструменты-фильтры
(function calling), а данные достаёт обычный запрос под RLS:

```ts
search_items({
  space_kind?:   string
  category_id?:  string
  purchased_from?: string   // ISO-дата
  purchased_to?:   string
  status?:       string
  sort_by?:      'energy_cost' | 'price' | 'purchased_at'
  limit?:        number
})
```

Так граница безопасности остаётся в базе, а не в тексте промпта. Никакая
инъекция в запрос пользователя не даст доступа к чужим данным, потому что
доступ ограничивает RLS, а не аккуратность модели.

### B-tier

#### 7. Объяснение энергорасчёта

Цифры уже посчитаны кодом; модель превращает их в человеческую фразу:
«Бойлер — 40 % твоего счёта. Снизь температуру с 75 до 60 °C, сэкономишь
≈120 грн в месяц».

Модель получает **готовые числа** в промпте и не имеет права их изменять —
только формулировать.

#### 8. Регламент ТО из инструкции

Из загруженного PDF вытащить график обслуживания и предложить готовые
повторяющиеся задачи: «фильтр — раз в 6 месяцев», «чистка теплообменника —
раз в год». Пользователь подтверждает список одним тапом.

#### 9. Еженедельная сводка от «Домового»

Раз в неделю короткое дружелюбное сообщение, собранное из детерминированных
данных:

> У микроволновки через месяц кончается гарантия, бойлер съел 180 грн, и пора
> менять фильтр в кувшине.

Работает на удержание и оживляет продукт: приложение перестаёт быть
справочником и становится персонажем. Данные для сводки собирает SQL-запрос,
модель только пишет текст.

### C-tier — осторожно

#### 10. Помощь в описании поломки

«Гудит и не отжимает» → структурированное описание для мастера и вероятные
причины.

Обязательны: дисклеймер, что это предположение, и **жёсткий запрет на советы
по газовому оборудованию и работам под напряжением**. Там, где ошибка опасна,
единственный правильный ответ — «вызови специалиста».

## Как интегрируем

```
Клиент (PWA)                Supabase Edge Function              OpenAI
   │  сжатое фото ≤1024px         │                                │
   │  + JWT пользователя          │                                │
   ├─────────────────────────────>│ 1. проверить JWT               │
   │                              │ 2. проверить членство в семье  │
   │                              │ 3. проверить ai_settings.enabled│
   │                              │ 4. проверить суточную квоту    │
   │                              │ 5. посмотреть в ai_cache       │
   │                              ├───────────────────────────────>│
   │                              │   Structured Outputs (strict)  │
   │                              │<───────────────────────────────┤
   │  черновик формы (JSON)       │ 6. записать ai_usage           │
   │<─────────────────────────────┤ 7. положить в ai_cache         │
   │                                                               │
   │  пользователь правит и подтверждает → обычная запись под RLS
```

### Ключевые решения

**Ключ OpenAI живёт только в секретах Supabase.** Ни при каких условиях не на
клиенте: всё, что попало в бандл, — публично. См. [ADR-009](07-decisions.md).

**Всегда Structured Outputs** (`response_format: json_schema`, `strict: true`).
Схемы генерируются из тех же zod-схем, что валидируют формы, — одно
определение на оба применения. Никаких «попроси JSON и надейся».

**Квоты и учёт.** `ai_usage` пишется на каждый вызов, `ai_settings`
хранит суточный и месячный лимит на семью. Проверка идёт **до** обращения к
модели. Расход виден пользователю в настройках.

**Кеш.** `ai_cache` по хешу входа: одна и та же табличка или один и тот же
текст модели не распознаются дважды.

**Сжатие изображений на клиенте** до ~1024px перед отправкой. Распознавание
шильдика стоит доли цента — но только если не отправлять 12-мегапиксельный
оригинал.

**Офлайн ложится в существующую очередь.** Нет сети — фотография встаёт в
outbox с пометкой «распознаем, когда появится интернет», а карточка создаётся
сразу, с одним названием. **Ни одна ИИ-функция не является обязательной:**
ручной ввод работает всегда, ИИ только ускоряет.

**Провайдер за интерфейсом.** Один слой `LLMProvider` с методами `extract`,
`embed`, `chat` — чтобы сменить модель или провайдера без переписывания фич.
Без over-engineering: именно один слой, а не абстрактная фабрика.

**Деградация.** Модель недоступна, квота исчерпана, ответ не прошёл валидацию
схемы — пользователь видит обычную форму и заполняет руками. Никаких тупиков.

## Приватность

Это чужая квартира, чужие чеки и чужие документы. Требования:

- **Явное согласие** при первом использовании: «фотография уходит в OpenAI для
  распознавания». До согласия ИИ-функции выключены (`ai_settings.enabled`
  по умолчанию `false`).
- **Переключатель на уровне семьи**, а не только своего профиля.
- **Ничего не отправляется фоном.** Только по прямому действию пользователя.
  Никакой автоматической индексации всех загруженных документов без
  подтверждения.
- **Минимизация.** В промпт уходит только то, что нужно для задачи: для
  распознавания шильдика — одна фотография, не вся карточка и не история
  семьи.
- **Логи без содержимого.** В `ai_usage` пишутся счётчики токенов и стоимость,
  но не тексты запросов и не изображения.

## Оценка стоимости

Порядок величин для планирования лимитов (уточнить по актуальному прайсу
перед запуском):

| Операция | Что уходит | Порядок |
|---|---|---|
| Распознавание шильдика | 1 изображение 1024px + короткий промпт | доли цента |
| Сканирование комнаты | 1 изображение + список категорий | доли цента |
| Индексация инструкции на 60 страниц | ~80 фрагментов на эмбеддинги | ниже цента |
| Вопрос к инструкции | 5 фрагментов + вопрос | доли цента |
| Еженедельная сводка | короткий текстовый промпт | пренебрежимо |

Реалистичный сценарий: семья заводит 40 единиц техники с распознаванием
шильдиков и загружает 10 инструкций. Разовые расходы измеряются центами,
дальше — почти ноль. Месячный лимит по умолчанию (`monthly_limit_usd = 5`)
поставлен с большим запасом и служит защитой от ошибок в коде, а не от
пользователя.

## Что проверить тестами

- Ответ модели, не проходящий валидацию zod, не попадает в форму и не роняет
  экран.
- Пользователь без членства в семье получает 403 от каждой `ai-*` функции.
- Превышенная квота возвращает понятную ошибку **до** обращения к OpenAI.
- Поиск по фрагментам инструкций не возвращает документы чужой семьи.
- При выключенном `ai_settings.enabled` ИИ-кнопки в интерфейсе отсутствуют.
- Повторный запрос с тем же входом обслуживается из кеша и не пишет новый
  `ai_usage`.
- Офлайн: снимок шильдика ставится в очередь, карточка создаётся сразу.
